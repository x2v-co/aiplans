# Kimi API 价格怎么比？我把国内、国际和第三方渠道拆开算了一遍

> 数据核验日期：2026-09-03。本文中的价格是当日快照，接入前请再次核对渠道
> 定价页、地区、限速和支付条件。

做 AI 应用成本评估时，我发现“Kimi 多少钱”其实不是一个足够明确的问题。它至少
混合了三件事：

1. 具体模型版本，例如 Kimi K2.5、K2.6、K2.7 Code 或 K3；
2. 购买渠道，例如月之暗面官方服务、国际渠道或聚合平台；
3. API token 计费与 Kimi 应用订阅。

如果不先拆开这三层，很容易拿不同模型、不同产品甚至不同币种的价格直接比较，
最终得到一个看起来精确、实际无法用于预算的数字。

## 我采用的计算口径

每条记录保留渠道原始结算币种。只有在需要跨渠道排序时才按同一汇率换算为美元，
账单金额仍以渠道显示的原始币种为准。

示例工作负载统一为：

```text
示例成本 = 100 万输入 token × 输入单价
         + 25 万输出 token × 输出单价
```

也就是：

```text
example_cost = input_price_per_1m + output_price_per_1m * 0.25
```

这个比例不是“标准用量”，只是为了让每行数据可复算。实际项目应替换成自己的
输入/输出 token 比例，并单独考虑缓存、批处理折扣和其他费用。

免费路由不会参与“最低付费价格”的选择，因为免费渠道往往有独立的限额、路由
规则或开放时间，不能直接当成稳定的生产价格。

## 四个当前样本

下面是 2026-09-03 快照中的四个例子。这里比较的是各自模型下记录到的最低渠道，
不是在不同模型之间判断能力或性价比。

| 模型 | 当前最低渠道 | 输入 / 1M | 输出 / 1M | 示例成本 | 已记录渠道数 |
| --- | --- | ---: | ---: | ---: | ---: |
| Kimi K2.5 | OpenRouter | US$0.45 | US$2.25 | US$1.0125 | 2 |
| Kimi K2.7 Code | OpenRouter | US$0.66 | US$3.40 | US$1.51 | 3 |
| Kimi K2.6 | 月之暗面 | ¥6.50 | ¥27.00 | 折算 US$1.9203 | 3 |
| Kimi K3 | 月之暗面 | ¥20.00 | ¥100.00 | 折算 US$6.5217 | 4 |

这组数据最值得注意的不是某一个最低价，而是下面几个问题。

## 1. 先锁定模型 ID，再比较渠道

K2.5、K2.6、K2.7 Code 与 K3 不是同一种商品。只搜索“Kimi API 价格”，然后把
所有结果按单价排序，会把版本差异藏起来。

比较顺序应该是：

```text
业务所需模型 -> 可用渠道 -> 输入/输出价格 -> 地区与限额 -> 最终成本
```

模型名里的 `Code`、`Fast`、`Thinking`、日期或批处理标识都可能对应不同价格和
限制。接入代码使用哪个精确标识，预算表就应该使用哪一行。

## 2. 输出比例会明显改变结果

如果应用主要做长提示词分类，输入 token 占比可能很高；如果是长文生成、代码生成
或推理结果输出，输出价格会更重要。

例如 Kimi K2.7 Code 的示例是：

```text
US$0.66 + US$3.40 × 0.25 = US$1.51
```

如果输出从 25 万 token 增加到 100 万 token，同一行的计算结果就会变成
`US$4.06`。因此，只看输入单价往往会低估生成型工作负载。

## 3. 国内与国际渠道不能只看换算价

即使模型系列名称相同，国内与国际服务也可能在以下方面不同：

- 账号注册与实名认证；
- 支付币种和付款方式；
- 网络访问与数据位置；
- 模型上线时间；
- 速率限制、合同和支持方式。

统一换算美元只解决“排序口径”问题，并不能证明两个渠道在运营层面等价。生产接入
时，官方渠道的账号归属、支持和额度稳定性可能比一个更低的展示价格更重要。

## 4. API 与 Kimi 订阅是两种产品

API 按 token 用量计费，适合软件集成、Agent 和批处理任务。Kimi 应用订阅覆盖的
是产品内功能和使用额度，不能直接当成通用 API credits。

预算时应该分别建立两张表：

- API：按输入和输出 token 估算；
- 订阅：按席位、功能与应用内额度比较。
