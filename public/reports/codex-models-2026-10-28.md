## Astra 的计算依据

主测 28 次，2,595,323 tokens；同一周窗口已用 89% → 92%，即时与延迟读数一致；控制会话累计计数未变。容量 = token / (额度变化 / 100)。读数各按 ±0.5 个百分点处理，差值为 3±1 个百分点，因此区间为 token / 4% 至 token / 2%。这不是统计置信区间。

前 4 次 Astra 试测单独保留（87% → 88%），不与主测跨区间合并，避免期间 Sol 和控制会话流量混入。

## 方法与限制

- 每次约 9.3 万输入 token（含缓存），要求短代码审查答案；唯一 nonce 不能消除客户端系统前缀缓存，以实际 usage 为准。
- 批次并发分别为 Astra 4/28、Sol 4/4/24/40；高并发不等同日常串行交互。104 次调用全部成功，未观察到工具执行；每次结果恰有一次 turn.completed。
- 普通输入 = input_tokens − cached_input_tokens；总量 = input_tokens + output_tokens，reasoning 不重复相加。缓存写入均为零，未标定写入权重。
- 每批均抓取所有返回额度窗口。本次只返回 10080 分钟周窗口；5 小时及月窗口未返回，不外推。
- 基线两次读数间隔约 3 秒，结束即时/延迟读数间隔至少 5 秒；采集时间不等于服务端结算时间，稳定读数不能保证完全结算。
- 控制会话为 Astra。Sol 批次存在控制会话流量，未用 API 标价猜测或扣除跨模型额度。
- 条件区间不是固定 token 保证额，也不能比较成纯模型扣量倍数；不同输入/输出/缓存配比需独立复测。共享额度不能相加。
- 原 Astra 高缓存混合控制会话结果作为历史证据保留，与本轮低缓存主测不可混算。
