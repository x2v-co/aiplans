## 方法与解释

1. 从已登录 Coding Plan 控制台的“配置 model name”读取官方可用名称，用既有订阅 coding 端点和本地 Claude Code 发起请求，按每个请求指定模型，不更改账号默认模型。
2. 沿用 kimi-k3 的合成代码审查任务，独立工作目录、关闭工具调用和持久会话。GLM-5.3-Flash 因扣量较小，第 5–24 次把源代码输入扩为 4 倍，前 4 次保留原长度。其他模型沿用原长度。相同文本不等于相同 token 数，不同模型的实际输出也不同，因此逐模型保留实际配比和长度差异；不能据此分离上下文长度对扣量的影响。GLM Flash 短输入与长输入观察到的单位 token 扣量有差异，因此主估算仅使用第 5–24 次长输入，前 4 次单独作为试测；差异与长度改变同时出现，并不能单独证明服务商存在某个具体加价阈值。
3. 每个模型先跑 4 次，额度变化较小时扩充样本；每批后停止请求，刷新三窗口并延迟复读。稳定后才进入下一批或下一个模型，所有成功调用纳入账本。
4. 每个窗口独立计算总容量 = 本模型总 tokens × 100 ÷ 已用比例增量（百分点）。显示精度 0.01 个百分点，假设每端舍入误差 ±0.005，区间 = tokens × 100 ÷（增量 ±0.01）。
5. 所有区间仅体现舍入边界，不是整体准确率或统计置信区间。月窗口保留为粗估，不按周数换算。

模型共用套餐额度池，容量不能相加。本报告是本次工作负载配比下的条件估算，不是服务商承诺、纯模型抵扣系数或跨模型固定 token 上限。没有缓存命中／写入的样本不能校准缓存权重；也没有通过 API 标价推定订阅抵扣。

控制会话在 Codex，不消耗火山套餐。未取得服务商全账户请求审计，不能完全排除其他设备调用；稳定复读不能排除更长的服务端结算延迟。仅采集了控制台相对重置倒计时，没有取得精确重置时间戳。
