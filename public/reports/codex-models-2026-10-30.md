## Astra

主测60次连续区间 49% → 53%，即时及延迟读数一致，重置时间不变，控制会话累计 token 计数未变。
普通输入 4,765,206；缓存读取 806,400；输出 8,733；缓存写入 0。总量 5,580,339。

点估计 = 总 token / 4%。每个整数读数按 ±0.5 个百分点处理，差值为 4±1 个百分点，因此范围 = 总 token / 5% 至 总 token / 3%。这是舍入条件区间，不是统计置信区间。前4次校准、32次扩展批分别保留，不跨越其他模型调用合并。

## Sol 下界的含义

32次扩展批和60次主测各有一次“Selected model is at capacity”错误；失败请求没有 usage，不能当作已知零消耗。最后主测59次成功，已知5,484,515 tokens，周读数48% → 49%，重置时间稳定，但控制会话计数有增量。

不把整段额度变化都归给 Sol，不用 API 价格扣除 Astra 消耗。若总已用额度的真实增量不超过2个百分点，且所有额外消费非负，则已知成功 Sol 调用消费也不超过2个百分点。于是本次成功负载配比的容量条件下界为 5,484,515 / 2% = 274,225,750 tokens。没有有限上界，也不发布点估计。该下界依赖计量已结算、线性扣量、无退款/重置/额度变化；任何假设不成立时不能使用。

## 方法和可比性

- 沿用10月28日合成Python代码审查输入，每次约9.3万输入 token，要求短输出；每次增加随机 nonce，缓存以实际 usage 为准。CLI只报告请求模型，未独立证明服务模型身份。
- 普通输入 = input_tokens − cached_input_tokens；总量 = input_tokens + output_tokens；reasoning 不重复计数。缓存写入为0，未标定缓存写入权重。
- 校准每批4次，扩展每批32次并发，主测60次、最多12并发。没有观察到工具执行。高并发负载不能代表所有日常交互。
- 每批前两次读数间隔至少5秒，结束即时/延迟读数间隔至少10秒；采集时间不等于服务端结算时间。
- 全部批次的窗口重置时间一致。模型共用额度池，容量不能相加。
- 不用模型API定价推断套餐扣量；页面美元等价价值沿用2026-10-29已核验的价格快照重算（不声称今天重新核验价格），只是API标价等价价值，不是套餐余额或扣量规则。
- Astra旧主测区间为64,883,075–129,766,150，新区间与其重叠；缓存及系统输入配比也有差异，不能用点估计之比证明升级倍率。
- 本轮在约53%已用时停止；不因错误无限追加调用。
